What's Inside a Policy File, and How a Robot Runs It

[Fundamentals]

Fundamentals: optimisation · neural networks · floating point · memory and the 1 kHz loop · GPUs · processes and the kernel · dynamics algorithms · deploying policies · policy files · how neurons compute · bits, delays and control. Measured on my workstation (Intel i7-9700, RTX 2070 SUPER, Ubuntu 24.04, Linux 6.8); code in the site's tools/posts/.

A trained policy reaches a robot as a handful of files: the network's weights, the statistics that normalise its inputs and outputs, a manifest that pins the contract (what each input means, in what units, at what rate), and checksums. I trained a small reaching policy, wrote it in four formats, and measured what each contains, how fast it loads, how a checkpoint can run code when it is opened, why a single flipped bit justifies a SHA-256 check, and what happens when the contract is broken. Sending joint angles in degrees, swapping two inputs, or skipping normalisation turns a 2.4 mm reach into errors of about half a metre.

1. A policy is code plus numbers

A neural-network policy is a function whose shape lives in code (a Python class: which layers, in what order) and whose behaviour lives in numbers (its parameters). A checkpoint stores the numbers. My example, a 6-128-128-2 network that moves a planar two-link arm toward a target, has 17,666 parameters. It was trained by imitating an analytic controller, and it reaches targets to 2.4 mm. To run it, a program must rebuild the class and pour the numbers in by name. If the class differs, loading fails, or it succeeds and computes something else. The file also has to carry everything the network assumed during training. The most important item is the mean and spread used to normalise each input and output.

All of the files are in the site's repository: manifest.json, bundle.sha256, and the checkpoints next to them.

  • .pt / .pth (torch.save) is a zip archive, listed above. It holds a pickled description of the saved object (data.pkl), one file of raw tensor bytes per tensor (data/0, data/1, …) and a few version records.
  • .ckpt usually means a training checkpoint (PyTorch Lightning popularised the name): the weights plus the optimiser's state, the step count and the hyperparameters, so training can resume. Adam keeps two extra numbers per parameter, so mine is 3.0 times the size of the weights alone. Deploy the weights, not the training checkpoint.
  • .safetensors is an 8-byte header length, a JSON header giving each tensor's type, shape and byte range, then the raw bytes. My writer for it is fifteen lines. Reading it runs no code and can map the file straight into memory. Here is the start of mine:
{
  "__metadata__": {"format": "pt", "obs": "q1,q2,target_x,target_y,hand_x,hand_y", "units": "rad,rad,m,m,m,m"},
  "model.net.0.weight": {"dtype": "F32", "shape": [128, 6], "data_offsets": [0, 3072]},
  ...  one entry per tensor
}
  • TorchScript .pt (torch.jit.save) and ONNX .onnx store the computation graph together with the weights, so the policy runs without its Python class: from C++ with libtorch, or in ONNX Runtime and TensorRT. That is how policies usually reach embedded computers.
  • Others follow the same pattern: Stable-Baselines3 saves a .zip of parameters and settings, JAX and Flax use .msgpack or .pkl, Keras .h5 or .keras, NumPy .npz.

All four of my files produce identical actions (maximum difference 0.0). They differ in size and in how long they take to open (Figure 1). The safetensors reader is fastest at 0.10 ms, against 1.5 ms for torch.load and 3.2 ms for the training checkpoint.

3. Opening a checkpoint can run code

Python's pickle format describes how to rebuild an object, and "call this function with these arguments" is a legal instruction. Any object can define __reduce__ to return such an instruction, so a checkpoint can execute code the moment it is loaded. I saved a policy with a harmless extra object that prints a line, and loaded it two ways:

torch.load(f, weights_only=False)
[this line was printed by code inside the checkpoint]

torch.load(f, weights_only=True)
    UnpicklingError: Weights only load failed. ...

With weights_only=True, the default since PyTorch 2.6, the loader accepts only tensors and plain containers and refuses everything else. Load checkpoints from others that way, prefer safetensors for sharing, and never pickle.load a file you did not make.

4. Checksums: why one bit matters

SHA-256 maps a file of any size to a 256-bit fingerprint. A bundle.sha256 file lists one fingerprint per file, in the format sha256sum writes and checks (sha256sum -c bundle.sha256):

67dcf722a9d7e53cca685f864e0c4fda8fa093d61d56b4dcac2453bb2735fdf3  manifest.json
7dbdab07cdb6d8e67545c731bbc3a5d4e5a77cadacfd9f0f8d215a04bef36de9  policy.pt
f675681ca33d02f0922c6f0e23fb0869074528c9ee2cc9ff3a9cf7644f9e9bed  policy.safetensors
bdb0c80495a3dcddb41b7af5ddd4d31d7cdc639c90460577b57d1a472ad6f8fe  policy_torchscript.pt
e733bdb3c886558b58362fe0ca96f7ef757b1957650967195ac37c881a1a67ca  training.ckpt

Two properties make this useful. First, any change to a file changes the fingerprint completely. Flipping a single bit anywhere in the checkpoint changed on average 128 of the 256 hash bits, never fewer than 97 (Figure 2, right), so a damaged or edited file cannot pass by accident. Second, one bit can matter. I flipped single bits of the policy's float32 weights 3,000 times (Figure 2, left). A flip in the lowest fraction bits changed the action by about 6×10−8 rad, which is harmless. Each higher fraction bit doubles the effect. A flip in the exponent changed the action by more than 0.1 rad in 7% of cases, and 41% of flips of the highest exponent bit did. A hash check at start-up is the cheap way to know the robot is running exactly the weights that were tested. Logging the hash with each run makes every result traceable to those weights.

5. The manifest is the contract

Weights say nothing about what the numbers mean. The manifest does. Mine names each observation entry in order, with its unit and frame; says that each action is an increment to a joint-position target, in radians, limited to ±0.15; and pins the policy rate (20 Hz), the tracker rate (1 kHz), the arm's geometry and the hash of the weights. Every one of those is a way to run the right weights wrongly. Figure 3 runs the policy in closed loop on 100 random targets with the contract broken in four ways.

  • Joint angles in degrees instead of radians: median error 498 mm instead of 2.4.
  • Two inputs swapped (target x and y): 467 mm.
  • Normalisation skipped: 491 mm.
  • Policy run at 40 Hz instead of 20 Hz: the same final error, because the loop is closed through the measured joint angles. But each action is a per-step increment, so twice as many steps per second moved the arm faster than at its trained rate: 8.4 rad/s at peak instead of 6.0. On hardware that is how velocity limits are hit.

None of these produces an error message. The network computes something plausible-looking from the wrong numbers. The only defence is to write the contract down, ship it with the weights, and check it at start-up.

6. How the robot runs it

The robot never reads the policy file. A program on the robot's computer does, and it hands the robot's controller numbers it understands: targets, gains, torques. The usual structure, which I use on hardware:

# once, at start-up
assert sha256("policy.pt") == manifest["weights_sha256"]   # the tested weights
assert manifest["robot"] == robot_config
assert manifest["policy_hz"] == RATE
policy = Policy()                                          # same class as training
ck = torch.load("policy.pt", weights_only=True)            # tensors only
policy.load_state_dict(ck["model"]); policy.eval()
n = ck["normalization"]; h = policy.initial_state()        # recurrent memory
for _ in range(20): policy(dummy_obs)                      # warm up first

# every policy step (20 Hz here)
obs = build_obs(robot_state)        # order, units, frame as in manifest
x = (obs - n["obs_mean"]) / n["obs_std"]
y, h = policy(x, h)
a = clip(y * n["act_std"] + n["act_mean"], n["act_low"], n["act_high"])
send_to_controller(a)               # targets and gains for the fast loop

Underneath, the tracker interpolates the targets and the robot's own 1 kHz impedance or torque loop turns them into motor currents (deploying policies, processes and the kernel, the 1 kHz loop). A recurrent policy also needs its memory reset at the start of each episode and carried between steps, exactly as in training.

7. Checklist

  • Ship a bundle: weights (safetensors or a weights-only .pt), normalisation, manifest, hash list.
  • Load with weights_only=True; never unpickle untrusted files.
  • Verify hashes at start-up and log the weights' hash with every run.
  • Check the manifest against the robot: input order, units, frames, action meaning and limits, rates.
  • Warm the policy up before enabling the robot, and clip actions to the manifest's limits.
