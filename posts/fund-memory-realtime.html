Caches, Latency and the 1 kHz Loop

[Fundamentals]

Fundamentals: optimisation · neural networks · floating point · memory and the 1 kHz loop · GPUs · processes and the kernel · dynamics algorithms · deploying policies · policy files · how neurons compute · bits, delays and control. Measured on my workstation (Intel i7-9700, RTX 2070 SUPER, Ubuntu 24.04, Linux 6.8); code in the site's tools/posts/.

A torque-controlled arm expects a new command every millisecond. Whether a learned controller can meet that depends less on arithmetic than on memory and on the operating system. I measured both on my desktop. A load from L1 cache takes 0.9 ns and one from DRAM 82 ns. A policy forward pass costs tens of microseconds, but a Python loop that sleeps between cycles misses a 1.1 ms deadline in 7–15% of them. The fixes are well known; what helps is seeing the numbers.

1. The memory hierarchy, measured

A pointer-chasing loop follows a random cycle through a buffer, one node per 64-byte cache line, so each load depends on the previous one and nothing can be prefetched. Its time per step is the latency of whichever level holds the buffer. A streaming read of the same buffer measures bandwidth. Figure 1 sweeps the buffer from 4 KB to 512 MB on an i7-9700 pinned to one core. Latency steps from 0.9 ns (L1, 32 KB) to 3.3 ns (L2, 256 KB), 10 ns (L3, 12 MB) and 82 ns (DRAM). Single-core read bandwidth falls from 147 to 120, 70 and 22 GB/s.

Two rules follow. A robot's per-cycle state, a few joints and a few 6×6 matrices, fits in L1 with room to spare, so arithmetic on it is nearly free and the overhead around it dominates. And anything that walks a large structure unpredictably (a scene graph, a hash map of contacts, a Python object graph) pays tens of nanoseconds per hop. Arrays laid out contiguously and processed in order are what the hardware is built for (Drepper 2007).

2. What fits in a millisecond

Figure 2 (right) times common per-cycle operations from Python on the same machine. A Python function call costs 0.07 µs; a NumPy operation on seven numbers costs 0.38 µs, almost all of it dispatch rather than arithmetic; a 6×6 solve 4.6 µs. A 64-256-256-7 policy takes 37 µs in single-threaded PyTorch and 15 µs written directly in NumPy, because PyTorch's per-operator overhead outweighs the arithmetic at batch size one. A MuJoCo step of the Menagerie Panda scene takes 29 µs. Everything fits in the budget. The risk is not the work; it is when the loop wakes up.

3. Waking up on time

I ran a 1 kHz loop four ways, three interleaved runs of 4000 cycles each, on a stock Ubuntu kernel with other work running (Figure 2, left).

  • Sleep 1 ms each cycle. The sleep adds to the work and the wake-up latency, so the median period is 1196 µs. The loop runs at about 836 Hz and drifts.
  • Sleep until an absolute deadline. The median period is right, but 12% of cycles (per run: 14%, 7%, 15%) were more than 100 µs late, with a worst case of several milliseconds.
  • Sleep until 0.2 ms before the deadline, then spin. 99% of periods within 10 µs.
  • Busy-wait. 99% within 0.4 µs, at the cost of a full core.

Robot interfaces are unforgiving about this. The Franka control interface expects a new command every millisecond, and too many late or missing commands abort the motion with a communication-constraints error. The standard recipe is a real-time kernel (PREEMPT_RT), a core isolated for the control thread, locked memory, no allocation or garbage collection inside the loop, and the 1 kHz loop in C++ while the learned policy runs slower and sets its targets and gains.

4. The sensorimotor connection

The nervous system's loops are slower than any of these: 20–45 ms for the short-latency stretch reflex, 50–100 ms for the long-latency response, more than 100 ms for vision (overview). It copes in two ways. First, muscles' intrinsic stiffness and viscosity respond to a perturbation immediately, before any reflex, so the fastest "loop" is mechanical. Second, forward models predict the consequences of commands to bridge the delay (internal models). Robots have the same layering on a faster clock. A 1 kHz impedance loop, or physical compliance, is the immediate mechanical layer. The policy at 10–50 Hz is the slow, predictive layer that sets its parameters. Getting the 1 ms layer right on a real-time thread is what lets the learned layer be slow.

5. Checklist

  • Keep per-cycle state in small contiguous arrays; avoid pointer-heavy structures in the loop.
  • At batch size one, framework overhead dominates; a hand-written NumPy or C++ forward pass can be several times faster.
  • Never sleep a fixed interval; sleep to an absolute deadline, then spin, on an isolated core with a real-time kernel.
  • Put the 1 kHz loop in compiled code and let the policy run slower above it.
