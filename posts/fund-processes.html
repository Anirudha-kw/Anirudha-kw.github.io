Processes, Threads and the Kernel Under a Robot

[Fundamentals]

Fundamentals: optimisation · neural networks · floating point · memory and the 1 kHz loop · GPUs · processes and the kernel · dynamics algorithms · deploying policies · policy files · how neurons compute · bits, delays and control. Measured on my workstation (Intel i7-9700, RTX 2070 SUPER, Ubuntu 24.04, Linux 6.8); code in the site's tools/posts/.

A robot's software is several programs on a general-purpose operating system: drivers, a state estimator, a controller, a learned policy, a logger. How they share cores and pass messages decides whether a 1 kHz loop holds. I measured both on a stock Ubuntu desktop. Passing a message between processes costs from 0.12 µs through shared memory to 31 µs through Python's multiprocessing queue. The surprise was the timer. On an idle core, a 1 kHz wake-up arrived 84 µs late at the median and 1.8 ms late at the 99th percentile, because the core had gone to sleep. Two unprivileged changes cut the 99th percentile to 13 µs.

1. Processes, threads and the scheduler

A process is an address space plus one or more threads; a thread is what the kernel schedules onto a core. Linux has scheduling classes. Ordinary threads share cores fairly; since Linux 6.6 the fair class uses EEVDF, which gives each runnable thread a virtual deadline and a time slice. Real-time classes, SCHED_FIFO and SCHED_RR, always run before any fair thread, and SCHED_DEADLINE reserves a runtime per period. PREEMPT_RT, the patch set that makes almost all kernel code preemptible so a high-priority thread waits microseconds rather than milliseconds, was merged into mainline Linux in 6.12. The machine I measured runs Ubuntu's 6.8 kernel with dynamic preemption in voluntary mode, a 1000 Hz tick, and no permission for my user to use SCHED_FIFO. Those are the defaults most people meet.

2. Messages between processes

Figure 1 gives the round trip of an 8-byte message between two processes pinned to different cores, 100,000 times each. Spinning on a shared-memory flag never enters the kernel: 0.12 µs, the cost of moving a cache line between cores twice, at the price of burning both cores. A pipe or a Unix socket costs about 4 µs: two system calls and a wake-up of the sleeping reader. Shared memory with a futex-backed condition variable is similar. UDP over loopback, the transport under most robot middleware, costs 10 µs. Python adds 10–25 µs: 16 µs for a multiprocessing pipe and 31 µs for a multiprocessing queue, which pickles every message and uses a feeder thread.

The medians are small. The tails are where control loops fail: the 99.9th percentiles run from 23 µs for a pipe to 68 µs for UDP, and single round trips took milliseconds when the receiving core was asleep or busy. Keep the fastest loop inside one process or one thread, and pass only set-points and gains across process boundaries at the slower rate.

3. Waking up on time

A control thread sleeps until its next deadline, usually with clock_nanosleep on an absolute time, and must wake promptly. I measured how late a 1 kHz wake-up arrives over 20,000 cycles under four conditions (Figure 2).

  • Default, idle core: 84 µs late at the median, 1.8 ms at the 99th percentile.
  • Core kept awake by a low-priority (nice 19) busy loop on the same core: the median falls to 52 µs and the 99th percentile to 55 µs. An idle core drops into deep sleep states; this CPU's deepest, C10, advertises an exit latency of 890 µs, and the 99th percentile on an idle core is set by waking up from them.
  • Timer slack set to 1 ns with prctl(PR_SET_TIMERSLACK), which any process may do: by default the kernel may delay an ordinary thread's timer by up to 50 µs to batch wake-ups, which is the 52 µs median above. With slack removed and the core awake: 2.2 µs median, 13 µs at the 99th percentile.

Rare stalls of about 3 ms appeared in every condition, including the best one. Something system-wide, outside my process's control, paused the core. A real-time kernel, SCHED_FIFO, isolated cores and firmware settings exist to remove exactly these. The general lesson is to measure the machine with a tool like cyclictest before trusting it with a 1 kHz loop, and to log missed deadlines in deployment.

4. Python in the loop

CPython's global interpreter lock lets only one thread run Python bytecode at a time, so threads help with waiting but not with computing. Processes avoid the lock but pay for serialising messages, which is the multiprocessing cost in Figure 1. Native extensions such as NumPy, PyTorch and MuJoCo release the lock while they compute. In practice: Python is fine for a policy at 10–50 Hz; the 1 kHz loop belongs in C++ or on the robot's own controller.

5. The sensorimotor connection

The nervous system is a distributed system with no shared memory. Every message is a spike travelling along an axon, with delays that grow with distance (how neurons compute). Its answer is architectural. Fast loops close locally: the spinal stretch reflex runs in 20–45 ms without the cortex. Slower loops above them send set-points and adjust the reflex gains (overview). That is the design a robot stack should copy. Put the fastest loop next to the hardware, in one thread, and let the learned policy talk to it at a lower rate with messages that can tolerate a late arrival.

6. Checklist

  • One process, one thread for the 1 kHz loop; shared memory or a lock-free ring buffer to the policy.
  • Absolute deadlines, a 1 ns timer slack, and a core that does not sleep (a real-time kernel and SCHED_FIFO if you can get them).
  • Pin threads to cores, keep background work off the control core, and never allocate memory or touch the disk in the loop.
  • Measure the tail latency of the machine you will run on, and log deadline misses.
